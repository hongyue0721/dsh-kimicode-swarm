# 平台说明与版本记录 / Platform Notes & Changelog

> 本文档记录插件在当前 DeepSeek Harness（0.2.2-rc.1）宿主环境下的运行边界说明，以及 0.1.x 至 0.2.x 的问题修复历史。
>
> This document summarizes platform behavior notes on DeepSeek Harness (0.2.2-rc.1) along with the issue resolution history across 0.1.x and 0.2.x.

## 当前运行说明 / Current Platform Notes

### 1. `/swarm-events` 进度流的同源访问模型

`/swarm-events` SSE 路由会校验请求头中的 `Origin` 与 `Host` 是否一致，自动拦截跨站请求；同源浏览器连接与本地无 `Origin` 请求可正常接入，并由前端 store 按 `sessionId` 过滤展示对应会话的进度。DSH 默认仅监听本地回环地址（localhost）；若通过 `--host` 将服务暴露到共享网络，建议在宿主外层配合反向代理或访问认证。

### 2. 手动取消批次在页面刷新后的展示形态

正常完成的批次会将完整结构化结果写入工具调用的 `presentationMeta`，运行中的批次则通过 SSE 补发内存快照，因此这两类状态在刷新页面后都能完整恢复逐行卡片视图。中途手动取消的批次通过异常通道向模型交付已完成结果与 `agent_id`，不含终态 `presentationMeta`；刷新页面后卡片会自动收起实时状态行，并在可展开的「原始结果」面板中完整保留已产出的 XML 结果文本。

### 3. 工作区文件并发协作

同一批次的子 Agent 共享当前工作区目录，宿主与插件层均不施加文件级互斥锁。对于包含代码修改或文件写入的场景，建议在拆解任务时按文件、目录或模块边界划分，避免多个子 Agent 同时写入同一文件。

## 0.2.x 更新与修复记录 / Fixed in 0.2.x

| 项目 | 背景与原因 | 解决方案 |
|---|---|---|
| 成功批次状态展示修复（0.2.1） | 宿主的工具调用投影状态对象不含 `status` 字段，前端旧判断逻辑将其误判为取消态 | 改为显式匹配 `'cancelled'` / `'aborted'` / `'interrupted'` 状态值，正常完成的批次准确渲染为绿色完成态 |
| Swarm 模式、Fork 与原生界面（0.2.0） | 0.1.x 无会话级触发门槛，预设仅作模型标签，前端为自定义样式 | 引入 `/swarm` 会话模式、`fork` 上下文派生、宿主 `agentPresets` 解析，以及基于宿主 UI 原语的原生进度卡片与配置面板 |
| 并发爬坡唤醒（O1） | 启动任务后未继续注册下一轮爬坡唤醒定时器 | 重构调度唤醒逻辑，每次激活任务后自动计算并安排下一次唤醒 |
| 宿主并发上限背压（O2） | 达到宿主 `maxActiveSubagents` 时抛出的 `ACTIVATION_LIMIT_REACHED` 被视为任务失败 | 将容量上限识别为正常背压信号，任务放回队首并在槽位释放或定时唤醒时自动重试 |
| 定时器单实例管理（O3） | 未排队任务的 `eligibleAt = 0` 导致重复唤醒与旧定时器残留 | 维护单一唤醒定时器，按实际最早可执行时刻精准调度 |
| 结构化限流识别（O4） | 宿主将模型限流作为 `stopReason: 'error'` 返回，旧逻辑依赖错误文本匹配 | 监听 `agent/request-error` 事件并按结构化 `failure.code === 'RATE_LIMIT'` 触发退避，同时在结果中保留完整错误信息 |
| 持续限流保护上限（O5） | 配额耗尽时无限重试会导致整批任务长期挂起 | 为单个任务设置最多 8 次限流重试上限（`maxRateLimitRetries = 8`），超限后清晰返回失败原因 |
| 取消后结果保留与续做（O6） | 子 Agent ID 仅在结束时返回，且取消后宿主默认丢弃常规返回值 | 在子 Agent 发布瞬间记录 `agent_id`；取消时通过带 XML 的错误交付已完成工作与 ID，供下一轮对话继续使用 |
| SSE 断线自动重连与补发（O7） | `EventSource` 瞬时波动即触发关闭，新连接缺少在途状态 | 瞬断交由浏览器自动重连，彻底断开时指数退避重连；服务端向新连接自动补发运行中快照与模式状态 |
| 结构化结果投影（O8） | 旧版前端从模型 XML 字符串反解析展示数据，易受正文特殊字符影响 | 工具内部直接输出结构化数据，模型 XML 与前端 `presentationMeta` 各自独立投影，并对 XML 封套标签做安全转义 |
| 超时与并发配置联动 | 配置项未接入调度器运行参数 | 新增并接入 `timeoutMs`（默认 2 小时）与 `maxConcurrency` 动态配置 |
| 已结束批次的快照释放 | 仅依赖前端卡片卸载清理快照，未挂载卡片的后台调用会残留内存状态 | 批次结束时服务端主动广播 `progress-end`，前后端同步释放对应快照 |

## 0.1.x 历史问题归档 / Historical Archive (0.1.x)

以下记录对应早期 0.1.x 版本（基于 DSH 0.1.1-rc.2 SDK）的代码审计与修复归档，均已在后续版本中解决。

### H1：`resume_agent_ids` 断点续做接线（已修复）

- **现象**：0.1.0 中 `spawn` 始终调用 `ctx.subagents.start()` 创建全新子 Agent，未按 `task.kind === 'resume'` 分流，导致传入的 `agent_id` 未生效。
- **修复**：在 0.2.0 迁移中接入宿主的 `sendMessage(parent, childId, content, { signal })` 与 `subagent/end` 事件监听，支持在原有所属子 Agent 会话上继续执行。

### H2：限流后并发容量恢复（0.1.2 已修复）

- **现象**：0.1.0 计算了限流后 3 分钟的 `recoveryAt` 唤醒时间，但唤醒后未将 `capacity` 递增，导致早期触发限流后整批任务一直维持低并发运行。
- **修复**：在满足 3 分钟无新限流窗口时自动将并发容量 `+1` 并更新时间基线。

### M1：客户端 progress store 内存清理（0.1.2 已修复）

- **现象**：`dropSwarmProgress(callId)` 未在批次结束后调用，长会话下历史快照持续累积。
- **修复**：在卡片进入终态及收到服务端 `progress-end` 事件时主动清理对应 `callId` 的实时快照。

### M2：完成后卡片保留 type/model 信息（0.1.2 已修复）

- **现象**：早期版本在任务完成后切换至 XML 反解析路径时丢失了 `type`、`model` 与 `mode` 属性。
- **修复**：改由结构化结果直接生成 `presentationMeta`，完整保留每项任务的模型、类型、耗时与工具统计。

### M3：启动异常时的状态区分（0.1.2 已修复）

- **现象**：`runAttempt` 捕获异常时将尚未启动成功的任务也标记为 `started`。
- **修复**：按是否已分配 `agentId` 精确区分 `started` 与 `not_started`。

### M4：调度器定时器 `unref` 处理（0.1.2 已修复）

- **现象**：调度器的唤醒定时器与单任务超时定时器未调用 `.unref?.()`，可能阻碍 Node 进程自然退出。
- **修复**：对内部定时器句柄统一调用 `.unref?.()`。
